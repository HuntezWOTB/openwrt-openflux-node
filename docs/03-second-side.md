# 03. Вторая сторона: телефон/ноутбук

Нода на роутере ничего не слушает — подключаться к ней напрямую не надо.
Вторая сторона подключается к тому же общему документу с тем же секретом.

## Что должно совпасть (все три пункта)

1. `Транспорт = mailru` (или тот, что выбран на ноде).
2. `URL` — буква в букву как на ноде. URL — это еще и контекст шифрования:
   отличающийся символ даст другой ключ и стороны не договорятся.
3. Общий секрет роутера (посмотреть — глазок `👁 Секрет` в панели,
   `cat /etc/openflux/secret.txt` — то же самое) + включенная
   шифрованная сессия (`--negotiate`).

Пример для CLI-клиента:

```sh
./openflux --role=client --inbound=socks5 \
  --transport=mailru \
  --url="https://cloud.mail.ru/public/XXXX/YYYY" \
  --encryption-key-file=secret.txt \
  --cookie-store=/tmp/cookies-mailru.json \
  --negotiate --socks5=127.0.0.1:1080 -dd
```

Готовый шаблон — `client.conf.example`.

## В мобильном приложении

Новый профиль -> клиент -> транспорт `mailru` -> вставить URL ->
вставить общий секрет -> включить шифрованную сессию -> режим VPN
на устройство -> Подключить и разрешить VPN.

## Проверка

- На роутере: `logread -e openflux | tail` — вместо `waiting for a client`
  появится установленная сессия и растущие счетчики пакетов.
- На устройстве: внешний адрес совпадает с домашним, открываются
  привычные сервисы.

Типичная ошибка: `peer sends classic-mode frames, but this side serves
Session peers only` в логе ноды — на второй стороне не включена
шифрованная сессия. Включите `--negotiate` и переподключитесь.
